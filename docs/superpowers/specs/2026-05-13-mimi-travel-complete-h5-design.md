# 咪咪出行 H5 完整实现设计

日期：2026-05-13

## 1. 目标

本设计用于把咪咪出行从当前“演示闭环 + 局部 Python 领域服务”推进到“本地可验收完整 H5 产品”。交付目标是：H5 端覆盖需求文档中的首期功能闭环，后端以 Python/PostgreSQL 作为核心业务事实源，第三方支付、地图、AI 通过可替换 provider 完成本地验收。

本阶段选择“本地可验收完整实现”，不把没有真实账号、密钥、商户配置和线上回调域名的第三方能力伪装成生产接入。所有外部能力都要有清晰 provider 边界，后续可替换为真实支付宝、微信支付、DeepSeek、高德和百度地图服务。

客户端范围为 H5 优先完整实现。小程序后续基于同一套 TS BFF API 对齐功能。

## 2. 总体架构

目标链路固定为：

```text
H5 React -> TypeScript BFF -> Python FastAPI -> PostgreSQL
```

职责边界：

- H5 只调用 TypeScript BFF，不直接访问 Python 服务。
- TypeScript BFF 负责统一前端 API、鉴权、DTO 转换、错误转译、provider 编排和兼容政策接口。
- Python FastAPI 作为主业务领域服务，负责用户、服务者、宠物、需求、报价、订单、支付、退款、消息、评价、风控、推荐、反馈和后台治理。
- PostgreSQL 替代当前 TS JSON FS，作为核心业务主存储。
- 当前 `DomainStore` 不再继续扩展为主业务实现，只用于迁移期兼容或逐步下线。

## 3. 实施路径

采用“后端事实源先行，H5 闭环跟进”的路径。

阶段顺序：

1. 补齐 Python/PostgreSQL 主模型、仓储、服务、状态机和测试。
2. 将 TS BFF 的核心业务 API 切换到 Python 主事实源。
3. 补齐 H5 页面、流程页和详情页，所有页面通过 API 真实读写。
4. 补齐本地支付、AI、地图、附件和通知 provider。
5. 补齐服务者工作台、评价、风控、后台审核、退款和争议处理。
6. 在 H5 稳定后，小程序按同一 API 做功能对齐。

## 4. 领域模块

核心领域模块以 Python/PostgreSQL 为准，TS 和 H5 只消费 API DTO。

### 4.1 身份与用户

支持用户登录、本地 session/token、角色 `customer`、`provider`、`admin`、手机号绑定和认证状态。管理员接口必须校验 admin 角色。

### 4.2 宠物档案

支持宠物昵称、品种、体重、疫苗、检疫证明、体型、默认携带方式等信息。下单时保存宠物快照，避免后续档案变化影响历史订单。

### 4.3 服务者画像

支持入驻申请、服务权限、服务区域、照护能力、车辆资料、审核状态、服务开关、服务半径和档期。展示层保留“闲人”的温度，交易和审核按正式服务者标准执行。

### 4.4 需求与报价

支持照护、出行、办证、托运协助等需求发布；支持需求大厅、附近筛选、服务者报名/报价、用户接受报价。报价被接受后，其余有效报价自动失效。

### 4.5 订单与状态机

订单状态包括待支付、已支付、待到达、服务中、已完成、已取消、退款中、已退款。所有状态变更写入 `order_events`。状态机禁止非法跳转。

### 4.6 支付与退款

支持本地支付宝 provider、本地微信 provider、支付单、主动查询、异步通知模拟、关闭支付、退款单和幂等处理。首期可验证全额、订金和尾款场景。

### 4.7 消息与通知

支持会话、消息、系统消息、报价消息、支付消息、位置消息、服务反馈消息和已读状态。首期使用轮询，不实现 WebSocket 或 SSE。

### 4.8 定位与导航

支持位置上报、订单参与方可见、高德/百度 URI 生成和 Web fallback。本阶段不接地图 SDK，不做真实路径规划。

### 4.9 评价与反馈

支持司机和闲人多维评分、标签、文本评价、服务反馈、图片/视频 URL 记录和反馈时间戳。

### 4.10 政策与 AI

支持政策知识库、区县查询、材料 checklist、政策收藏、复制、AI 问答和引用来源。默认使用本地 RAG provider，预留 DeepSeek provider 配置入口。

### 4.11 后台治理

支持管理员审核服务者、查看订单、查看退款、处理投诉和争议、下架异常服务者、记录管理操作日志。

核心 H5 闭环：

1. 用户登录。
2. 维护宠物档案和常用地址。
3. 发布照护、出行、办证或托运需求。
4. 在需求详情查看推荐服务者和报价。
5. 选择服务者生成订单。
6. 订单确认后进入支付确认。
7. 本地支付 provider 返回支付结果。
8. 订单进入待到达或服务中。
9. 双方在会话中沟通并上报位置。
10. 服务者提交照护反馈。
11. 用户确认完成并评价。
12. 异常时发起退款、投诉或争议。
13. 管理员后台处理审核和争议。

页面表单要覆盖需求文档字段，但使用分组或分步方式，避免单页过长。所有需求、订单、支付、退款和争议页面都要展示明确状态和事件时间线。

## 7. Provider 设计

### 7.1 支付 Provider

实现 `LocalAlipayProvider` 和 `LocalWechatProvider`。能力包括创建支付、查询支付、模拟异步通知、关闭支付、退款和幂等处理。返回本地可验证支付 URL 或参数，不声明已接入真实支付宝或微信。

### 7.2 AI Provider

实现 `LocalRagProvider`，基于知识库检索生成结构化回答、引用来源和材料提醒。预留 `DeepSeekProvider`，没有 key 时不启用。

### 7.3 地图 Provider

实现高德和百度 URI 生成、Web fallback 和参数校验。不接 SDK，不做实时路线规划。

### 7.4 附件 Provider

首期记录 URL 和本地示例资源，不实现对象存储上传。

### 7.5 通知 Provider

首期写入消息表和系统消息，不实现短信、微信模板消息或站外推送。

## 8. 错误处理与安全

所有 API 返回统一错误结构：

```json
{
  "code": "ORDER_INVALID_STATUS",
  "message": "订单当前状态不允许该操作",
  "details": {},
  "requestId": "req_xxx"
}
```

安全规则：

- 支付、订单、报价、退款必须做幂等。
- 订单状态机禁止非法跳转。
- 需求被选中后，其余有效报价自动失效。
- 位置、会话、订单只允许参与方访问。
- 管理后台接口必须校验 admin 角色。
- 第三方 provider 不可用时返回明确降级状态，不自动伪造真实成功。
- 日志不得记录完整支付敏感参数。

## 9. 测试与验收

测试分三层：

- Python 单元和接口测试：仓储、状态机、匹配、定价、风控、支付退款、消息、后台审核。
- TS BFF 测试：DTO 转换、鉴权、错误转译、provider 编排、前端 API 契约。
- H5 验收测试：登录、发布需求、报价、下单、支付、消息、导航、反馈、评价、退款、争议、后台审核。

固定验收命令：

- `pnpm --filter ./server run build`
- `pnpm --filter ./client run build`
- Python 测试命令在确认 Python 环境后固定，例如 `conda run -n <env> pytest`
- Docker compose 联调：前端、TS BFF、Python、PostgreSQL 全部健康后跑冒烟请求。

## 10. 验收口径

本阶段完成时应满足：

- H5 能完整跑通照护需求和出行需求两条主链路。
- 服务者可以入驻、被审核、报价、接单和提交反馈。
- 用户可以维护宠物档案、常用地址、收藏政策、支付、退款、评价和投诉。
- 管理员可以审核服务者、处理争议、查看订单和退款。
- 所有主业务数据写入 PostgreSQL，不依赖 TS JSON FS。
- 支付、AI、地图在本地 provider 下可验收，并具备真实 provider 替换边界。
- 小程序不在本阶段实现完整功能，但不得破坏现有小程序演示能力。
